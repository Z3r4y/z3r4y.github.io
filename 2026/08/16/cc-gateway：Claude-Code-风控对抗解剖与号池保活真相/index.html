cc-gateway：Claude Code 风控对抗解剖与号池保活真相

Z3r4y
2026-08-16
Cyber Security
Claude Code, LLM Security, OAuth, Reverse Proxy, Risk Control, Telemetry

项目：motiful/cc-gateway（v0.2.0-alpha，MIT）

一句话：cc-gateway 是一个把 Claude Code 的遥测身份「归一化」成单一画像的反向代理。它解决的是设备级证据，不是行为级证据；它最真实的商业场景不是「个人多设备隐私」，而是「订阅号池转 API 的保活率」。

1. 项目是什么

cc-gateway 站在 Claude Code 与 Anthropic API 之间，把请求体和遥测里的 device_id、email、环境指纹、进程指标全部改写成一个 canonical 画像，同时集中持有 OAuth，让下游客户端「零登录」接入。

  • 零框架 TypeScript（Node 22+），src/ 约 900 行，16 项测试全部通过
  • README 自述的威胁模型：Claude Code 收集 640+ 遥测事件类型、3 条并行上报通道、40+ 环境维度指纹、每 5 秒回传一次

2. 风控对抗的四层机制

2.1 身份恒定

/v1/messages 的 metadata.user_id 是 JSON blob，内含 device_id / account_uuid / session_id。网关把它整个 parse 出来、把 device_id 覆盖为 canonical 身份（src/rewriter.ts:75-81）；/api/event_logging/batch 遥测里的 device_id、email 同样归一（src/rewriter.ts:211）。

效果：同一账号在 N 台机器上，服务端看到的所有设备指纹都指向同一个人。

2.2 环境恒定

env 对象不是逐个 patch，而是整对象替换成 buildCanonicalEnv()（src/rewriter.ts:252）：platform、arch、node_version、terminal、package_managers、runtimes、is_ci、is_claude_code_remote…… 全维度写死。

连系统提示里注入的 <env> 块（Working directory / Platform / Shell / OS Version）都被消毒重写，防止「system prompt 里写着一台机器、遥测 env 里是另一台机器」的对不齐。

2.3 机器恒定

process 指标由 buildCanonicalProcess()（src/rewriter.ts:278）掩码：constrainedMemory（物理内存）、heap、RSS 都归一成 canonical 值，避免「同一账号一会儿 16G 内存、一会儿 8G」的硬件泄漏。

2.4 代理痕迹消失

  • 剥离 x-anthropic-billing-header（含 per-session 指纹 hash，src/rewriter.ts:118）；顺带的彩蛋是 README 声称能开跨会话 prompt cache 共享、省 ~85% system prompt 成本
  • 删除遥测里的 baseUrl / base_url / gateway 字段（src/rewriter.ts:233-235）
  • CCH hash 逆向（src/rewriter.ts:6-15）：billing header 里的 cc_version=2.1.81.a1b; cc_entrypoint=cli; 是服务端用来校验会话的，其指纹 hash 的算法是 SHA256("59cf53e54c78" + 首条用户消息第[4,7,20]位 + 版本号) 取前 3 位。网关按「改写后的消息」重算 hash，保证服务端看到的 billing 头与消息体自洽；无用户消息时用随机 2 字节兜底（src/rewriter.ts:9）

2.5 集中 OAuth + 单 IP 出网

客户端机器从不接触 platform.claude.com：refresh token 只存在网关侧（src/oauth.ts:28），网关负责刷新并注入真实 token 到 x-api-key（src/proxy.ts:129）。所有请求从网关单 IP 出网。

3. 为什么「用了 ANTHROPIC_BASE_URL 本身就是异常信号」

关键区分：这条判断只对订阅 OAuth 群体成立。

  • 官方 cli 默认只连 api.anthropic.com / platform.claude.com；把 ANTHROPIC_BASE_URL 指向第三方域，意味着流量路径偏离官方基线
  • 官方 LLM gateway 连接文档 自己就承认：即使配了网关，Claude Code 仍会把版本检查、遥测、错误报告等后台流量绕过网关直连 Anthropic —— 即「网关路径外始终存在官方直连信号」，服务端从遥测里看到非官方端点并不意外
  • 官方 gateways 文档（2026-07）明说：Anthropic 不认可、不维护、不审计第三方 gateway 产品 —— 第三方网关路径本身就是「非官方路径」
  • 佐证：anthropics/claude-code issue #49932 里，设置 ANTHROPIC_BASE_URL 后组织级策略（含 OAuth 约束）会被绕过 —— 官方清楚知道这个变量是「绕路」入口

但对 API token 用户（sk-ant-api03-），官方没有设备数限制，token 本身是按量计费的商品，跨机器使用是正常用法，不存在「一台 token 被多台机器用」的异常。所以「base_url = 异常信号」这句话翻译过来其实是：这是一个面向订阅账号风控的判断，而订阅账号恰恰是号池生意的标的。

4. 真实泛化场景：号池转 API 保活

README 的叙事是「个人在多台机器上管理自己的身份」，但架构上处处在为另一种场景优化：

  • 集中 OAuth：个人自用的话，每台机器自己登录自己的账号就够了，根本不需要「客户端零接触」
  • 单 IP 出网：个人多设备从不同 IP 访问反而更「正常」，统一出网是号池才需要的
  • billing header 剥离 + prompt cache 共享：省的是账单。对个人是省几块钱，对号池是按账号计的成本
  • 客户端零配置 launcher：这是「卖给下游」的产品形态，不是自用形态

所以真实泛化场景是：

「保活率」问题的本质：一个订阅账号被 N 个消费者并发使用，服务端看到的是「同一个账号，N 台机器、N 个环境、N 个 IP、N 条行为曲线」。cc-gateway 把 N 台机器压成一个 canonical 画像，把「N 个设备在用一个账号」的设备级证据抹平 —— 这就是「防止上游被封号」的机制解释。

5. 暴露面：网关解决不了什么

  • 行为曲线：请求频率、token 消耗速率、活跃时段、会话并发数。N 个消费者 = N 倍于单人的消耗速率，这个维度网关完全没碰。V2EX 上已经有人提到 A 社在用 AI 行为分析
  • IP 信誉：号池出网 IP（尤其被大量账号复用的 IP）本身就是黑名单常客；网关只保证「一个账号一个 IP」，不保证「这个 IP 干净」
  • 多账号关联：池内所有账号共享同一套 canonical profile 模板，账号聚类反而更简单了
  • 手写画像自洽性：env/process 是固定值 + 随机抖动，多账号长期累计会失真（比如池内 20 个账号永远同一内存值）；硬编码逆向常量（CCH salt、positions）一旦官方改算法就全部失效
  • 官方入局后格局变了：claude 二进制已内置官方 gateway（2026-06-28 发布），官方文档明确对网关端点做检查（Anthropic 运营的公共网关端点有豁免，自托管网关要过私有地址/代理检查）—— 第三方网关本身正在被纳入检测面

6. 调研：有没有新的 cc-gateway 分析文章/博客

结论：没有。 截至 2026-08，公开渠道没有一篇独立的深度技术剖析（把 rewriter 逐条改写逻辑对源码分析的那种）。能拿到的素材分四类：

新闻通稿（2026-02~03）

  • chinaz、cnBeta 同源稿：640+ 遥测、5 秒/次、40+ 异常检测；口径都是「只能提升检测难度，不能完全规避」

使用指南（2026-04~05）

  • CSDN 使用指南（最完整中文部署指南）
  • Inferri 导读（点出局限：仅 macOS Keychain、单向归一化）
  • github-star 源码剖析（2026-04 时约 2.2k stars）

社区一手反馈（信息量最大）

  • LINUX DO 效果帖：「配完半小时被封号」—— 设备级归一化救不了行为/IP 证据
  • LINUX DO 中转劫持帖：印证号池行业普遍使用同类路径替换手法
  • V2EX 虚拟机躲封讨论：CC 会上报时区、会检测 anthropic_base_url 是否中转域名；猫鼠游戏论
  • V2EX 号池行业内幕：A 社高强度封号、账号平均存活约 1 小时、按卡 BIN 封号

生态大事件（2026-06~08，最值得关注）

  • 2026-06-28：官方 Claude apps gateway 发布，网关内置在 claude 二进制里，面向 Bedrock / Claude Platform on AWS / Google Cloud / Microsoft Foundry
  • 2026-07：官方 gateways 文档声明不认可/不审计第三方网关；LLM gateway connect 支持 ANTHROPIC_BASE_URL 指向组织网关，但说明后台流量仍直连官方
  • InfoQ 报道

同类项目

  • alexazhou/gt_ai_gateway：V2EX 活跃的防追踪 AI 网关
  • fengerwoo/CCGate：号池二次分发代理

7. 结论

  • cc-gateway 是「设备级证据」对抗工具：身份、环境、进程、出网四层恒定
  • 「ANTHROPIC_BASE_URL 是异常信号」只对订阅 OAuth 成立，这句话本身就暴露了它面向的场景
  • 真实动机是号池转 API 的保活率；行为曲线、IP 信誉、多账号关联是它不覆盖的暴露面
  • 官方入局（内置网关 + 声明不审计第三方网关 + 网关端点检测）意味着对抗维度在升级
  • 合规上：订阅账号转售/多消费者共用在 Anthropic ToS 下属于高危违规，号池生意整体处在灰色地带 —— 分析归分析，别把它当商业方案
