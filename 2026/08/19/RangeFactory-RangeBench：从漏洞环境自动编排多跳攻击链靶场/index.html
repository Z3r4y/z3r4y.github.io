RangeFactory / RangeBench：从漏洞环境自动编排多跳攻击链靶场

Z3r4y
2026-08-19
Paper Reading
Agent Security, Automated Penetration Testing, Benchmark, LLM Security, Paper Reading

论文：RangeFactory: Scalable Construction of Multi-Hop Cyber Ranges
链接：arXiv:2608.09526 · HTML 全文 · PDF
提交：2026-08-10，16 页 2 图，cs.CR / cs.AI；Hanlin Jiang 等 13 人，通讯作者 Ding Li
代码/数据：暂无公开下载（受控、research-only、role-based 发布）

怎么把一堆”单独都能打穿”的漏洞环境，自动变成一条条”端到端验证过”的多跳攻击链，再拿去量 LLM 攻击 Agent 能不能把整条链走完？

1. 这篇论文在解决什么问题

现实攻击不是单点利用，而是跨主机、跨网段的持续推进。要系统性研究 LLM 攻击 Agent 的”持续攻陷”能力，需要多跳 cyber range：攻击者必须用前面打下的立足点去够到不同网段的后续目标。

已有资源分三类，各有缺口：

路线 代表 缺什么
单漏洞任务规模化 CVE-Bench、CyberGym、CVE-Factory、PACEbench 的 A/B 类 每个任务停在孤立利用，测不了跨位置的持续攻陷
专家手工多主机靶场 AgentCyberRange、Folkerts 等人的 multi-step 场景 端到端，但只有一小撮专家设计、固定的场景，难以扩展
自动场景生成 VSDL、SecGen、CRACK、ARCeR、约束式合成 能自动部署环境，但跨漏洞依赖仍要专家预先指定

RangeFactory 想补的洞是最后这个：不需要 per-range 专家标注，把 Vulhub / CVE-Factory 的漏洞环境供应，自动变成端到端验证过的多跳靶场。

自动化的中心难点，是让两个”各自独立可利用”的漏洞在同一条攻击里连续执行。论文把阻碍拆成两类依赖：

  • 能力依赖（capability dependency）：前一个攻击是否产出后一个攻击需要的能力。读文件能力撑不起一个要求命令执行的后续利用。
  • 运行时依赖（runtime dependency）：具体攻击过程换到新立足点后还能不能跑。比如回调被网络策略挡掉、目标机缺工具。

直接枚举所有组合再逐个执行，候选空间爆炸。论文的策略是：用真实攻击提取依赖 → 模板引导编排消解已知依赖 → 端到端执行验证组合后才浮现的运行时依赖。一句话：把 range 构造看成”依赖解析”问题。

2. 核心抽象：CVE Capability Atom

RangeFactory 的最小构造单元，是把”能打穿的漏洞环境 + 依赖信息 + 可复用攻击过程”打包成的 CVE Capability Atom。四个字段：

字段 语义
exploit_access 利用的结构化前置条件：攻击向量、所需权限、服务协议/端口
capability_grants 探测验证过的可利用后能力，绑定到具体身份与证据
exploit_guide 验证过的攻击过程：工具、材料、认证、回调等运行时需求
poc_materials exploit_guide 引用的 PoC 材料

关键设计是只信验证过的能力。capability_grants 来自封闭本体：

能力 含义
execute_command 以记录的身份在目标主机执行命令
read_file / write_file 读写该身份可访问的文件
network_vantage 从目标主机所连网络发起网络交互
read_credential 拿到场景资产表示的凭据
authenticate 用拿到的凭据建立认证访问

编排时用固定闭包规则推导，不做自由推断。当前规则里 execute_command ⇒ {read_file, network_vantage}，即命令执行隐含文件读和网络视野；凭据和认证不随命令执行自动成立，必须主机、身份、访问策略三者匹配。CWE、MITRE ATT&CK 这类分类只当描述性元数据，不能替代已验证的能力授予。

Atomization。 Exploiter 部署可复现的单漏洞环境，配一个和漏洞影响对齐的私有目标，在反馈中适配攻击；独立 verifier 确认命中后，把过程、利用条件、观察到的运行时依赖蒸馏成 exploit_guide。Explorer 复用 Exploiter 的环境，探测漏洞影响还能支撑哪些后续动作，产出 verified 的 capability_grants。这一阶段对每个漏洞环境只做一次，产物可以在大量候选 range 间复用。

Orchestration。 Generator 参考公开架构资料，产出参数化的企业风格模板：固定网络结构和通信策略，从外部入口到最终目标标出一条攻击链骨架，每个被穿越的层预留一个 CVE 槽位，背景业务资产独立参数化以控制搜索空间。Composer 按攻击链顺序做绑定：取服务要求与模板位置兼容的 Atom，检查前面累积的能力是否满足下一个 Atom 的 exploit_access，绑定后更新能力集；部分链一旦违反依赖立即剪枝回溯。模板 + exploit_guide 还能在部署前查掉一批运行时要求（执行位置、材料投递），剩下只能在组合环境里浮现的交给端到端执行。

Validation。 Executor 拿着 Atom 执行产物把各跳利用组织成端到端攻击，随立足点和环境变化做适配；独立 verifier 按顺序核对对 Agent 隐藏的私有目标。只有完整打完的候选才被接受；失败的交给 Diagnoser 区分两类原因：执行失败退回 Executor 做有界重试，组合不兼容则作为不兼容记录存下来，供后续编排检索。失败的证据会反哺后续候选生成——这是它和一次性过滤器的区别。

4. 构造漏斗与质量

资源来自 Vulhub（公开、GitHub 20.9k+ star）和 CVE-Factory（arXiv:2602.03012），筛选标准：可部署网络服务 + 影响可经网络交互验证。漏斗如下：

阶段 数字 说明
Atomization 257 → 239 93.0% 成功转成 Atom；失败源于缺构建产物或复现不稳定
覆盖 122 产品 CVE 覆盖 2010–2026 年
Orchestration 23,789 提案 → 1,840 候选 剪掉 21,949 个能力/运行时依赖不满足的，预部署剪枝 92.3%
Validation 1,840 → 1,148 端到端验证通过率 62.4%
最终结构 287 链 × 4 上下文 287 个不同有序 Atom 链，每个在 4 个匹配网络上下文实例化
  • 模板：5 个三层模板（DMZ → 内网应用 → 数据网，每层一个漏洞节点），4 种背景资产规模（约 7/12/31/50 个可见节点）→ 20 个网络配置。1,148 = 287 × 4，四个上下文共享同一模板和 Atom 链，只换背景资产，从而把”攻击链多样性”和”周边网络变化”分开。
  • 覆盖：1,148 个实例用到了 239 个 Atom 中的 213 个（89.1%）、113 个产品、全部 20 个配置。
  • 成本：平均首轮验证 16.2 分钟；每个保留 range 摊 26.0 worker-minutes，验证总成本 496.8 worker-hours（大量是自动化 Agent 时间）。

质量审计（150 个已接受 range 随机抽样，独立复核）：

审计项 通过率 说明
行为保持 146/150（97.3%） 注入漏洞保留了源漏洞的安全影响
Atom 标注一致 142/150（94.7%） exploit_access、能力类型、身份、scope 与攻击状态一致
误拒率 12/150（8.0%） Kimi-K3 用同样工件/工具/预算复检 150 个被 DeepSeek-V4-Pro 拒掉的候选，找回 12 个

注意：每个保留 range 都有一条完成全部私有目标的”构造 witness”，但这不等于没有别的攻击链——审计只支持”行为保持 + 依赖语义正确”，不断言路径唯一。

5. 为什么依赖引导和端到端验证都不可省

依赖引导的消融（从同一 Atom 库和模板抽 200 个匹配提案，同等提案/验证预算）：

组合策略 环境有效 端到端有效
随机绑定 88.5% 4.0%
元数据匹配（CVE/服务描述） 91.0% 13.5%
能力匹配（capability 接口） 94.0% 43.5%
完整编排（+ 运行时需求检查） 95.0% 60.0%

环境有效性四档差别很小，端到端有效性从 4% 拉到 60%——说明瓶颈不在”环境起不起来”，而在”链连不连得上”。能力信息贡献最大，运行时要进一步消掉模板约束冲突。

端到端验证的必要性：把完整编排产出的 200 个候选深挖，190 个过了环境检查，但只有 89 个在 Executor 首轮就打穿；诊断引导重试再救回 31 个，最终接受 120 个。也就是说只做环境验证会误收 70 个”没有端到端攻击成立”的候选。单漏洞环境里不存在的运行时依赖（组合后的路由、回调可达性）只有完整攻击能测出来。

Diagnoser 的两种效果（等预算对照）：77 个执行失败里，额外 100 轮、无诊断只救回 14 个，诊断引导救回 31 个；24 个组合冲突里，没有不兼容记忆时 21 个在下一批重复出现，带上记忆后降到 8 个。诊断既修当前验证，也积累跨候选的编排证据。

6. RangeBench 评测设计

  • 实例：1,148 个端到端验证过的 range。每个 range 在 DMZ / 内网应用 / 数据网三层各放一个私有目标，一次 rollout 同时产出 1 跳 / 2 跳 / 端到端三个测量；深层目标只有拿到前序立足点才可达，所以三个深度共享同一入口漏洞和链前缀，深度差异不能归因于入口更难。
  • 任务信息层级（嵌套，无任何层级给 PoC / Exploit Guide / 构造轨迹 / verifier 状态）：
层级 Agent 可见信息
L0 入口地址 + 最终目标
L1 L0 + 网络拓扑
L2 L1 + 目标服务、CVE 映射、所需凭据
  • 协议：每模型–range–条件一次 rollout（pass@1）；预算 300 turns / 1 小时；Kimi-K3 用 temperature 1（其端点允许的最小值），其余模型 temperature 0，其余采样参数走 provider 默认。瞬态 API 错误重试，部署/基础设施故障重跑且不计 Agent 失败；拒答、提前终止、目标未达、预算耗尽都算失败。Agent 看不到 Atom 执行产物。
  • 单元数（纠正）：1,148 实例 × 3 信息层级 = 3,444 rollouts/模型，× 4 模型 = 13,776 个 rollout 总量（不是”每模型 13,776”）。
  • 环境：Docker + ContainerLab + Ansible 编排的 Linux 容器化企业多段网络；模型走远程 API，端点不暴露公共 seed 接口。

7. 结果

L2 总体表现（端到端成功率 / 链进度 / 中位工具调用 / 中位耗时）：

模型 端到端成功 链进度 工具调用 耗时(min)
Kimi-K3 55.7% 64.6% 138 44.6
GLM-5.2 41.2% 51.2% 145 46.8
DeepSeek-V4-Pro 36.2% 46.2% 152 48.5
GPT-5.6-Luna 23.5% 32.9% 86 27.4

GPT-5.6-Luna 成本显著更低（86 次调用 / 27.4 分钟），但它更早放弃——低成功率和过早终止是绑在一起的。

攻击深度（L2，同一批 rollout 逐层看）：

模型 Hop1 Hop2 Hop3(E2E) H3|H1（拿到入口后走完全链） 持续攻陷缺口
Kimi-K3 73.8% 64.2% 55.7% 75.5% 24.5%
GLM-5.2 62.8% — 41.2% 65.6% 34.4%
DeepSeek-V4-Pro 57.8% — 36.2% 62.6% 37.4%
GPT-5.6-Luna 44.3% — 23.5% 53.0% 47.0%

核心发现——持续攻陷缺口：成功打进入口漏洞的 run 里，还有 24.5%–47.0% 走不完剩余路径。入口易、续攻难，而且缺口随深度累积。

任务信息层级（端到端成功率）：

模型 L0 L1 L2
Kimi-K3 15.4% 20.1% 55.7%
GLM-5.2 10.8% 14.9% 41.2%
DeepSeek-V4-Pro 8.1% 11.7% 36.2%
GPT-5.6-Luna 4.5% 6.6% 23.5%

L0→L1 增益很小，L2 是质变（给的是公开 CVE，可能混入模型对漏洞的熟悉度，论文自己承认这一点）。但信息给满，最好模型也失败近半——持续执行难度不是靠情报就能抹平的。

网络规模（L2，约 7/12/31/50 节点）：

模型 规模 端到端成功 工具调用 耗时(min)
Kimi-K3 none→high 60.8% → 50.2% 104 → 177 33.2 → 56.7
GLM-5.2 none→high 46.1% → 36.0% 110 → 189 34.4 → 60.0
DeepSeek-V4-Pro none→high 40.9% → 30.6% 114 → 198 35.7 → 63.7
GPT-5.6-Luna none→high 29.0% → 19.2% 70 → 106 19.0 → 35.0

网络变大对最终成功率影响”温和”（−9.8~−10.6pp），但对交互成本是放大器：工具调用 +51–74%，耗时 +71–84%。背景资产多了，Agent 把大量预算花在探索诱饵上。

8. 轨迹语料

  • 收集：1,148 条构造期 guide-assisted 轨迹 + Kimi-K3（表里最强的无引导 Agent）在每个实例上收 4 条自主 rollout（L2×2、L1×1、L0×1）→ 5,740 条原始轨迹。
  • 清洗：移除 73 条部署/运行故障中断 + 48 条交互记录不完整 + 78 条重跑重复 → 5,541 条。
  • 组成（端到端成功 / 部分进展 / 无进展）：
语境 数量 端到端成功 部分进展 无进展
Guide-assisted 1,148 100% 0% 0%
L2 2,215 55.7% 18.0% 26.3%
L1 1,095 19.9% 32.6% 47.5%
L0 1,083 15.1% 31.2% 53.7%
合计 5,541 49.9% 19.7% 30.4%
  • 结构：每条记录保留任务上下文、Agent–工具交互、预算和 provenance（range / collector / 信息层级 / 引导模式）；verifier 记录每个目标的首个完成 turn、最深已验证跳、最终结果；milestone turns 能定位同一任务上不同行为的分叉点。
  • 质量策略：攻击失败不筛除，只要日志完整且 verifier 能判定进度就保留，把”没打下来”和”数据采集故障”分开。论文只评估语料结构与质量，不声称下游训练收益。

9. 统计严谨性（论文自己把底牌亮了）

  • 1,148 个实例不是独立单元：同链 4 个上下文是匹配观测。以 G=287 个链组为独立单元，Hoeffding 界给出 95% 区间半宽 ±8.0pp（如 Kimi-K3 E2E [47.7%, 63.7%]）。
  • 相邻模型差距 14.5 / 5.0 / 12.7pp，配对最坏情形界都包含 0；网络规模效应（−9.8~−10.6pp）的配对界同样包含 0。论文的立场是：点估计刻画的是 balanced benchmark 上的 pass@1，细粒度排名稳定性需要多次 rollout，当前协议下不可断言。
  • Kimi-K3 temperature=1 是端点约束，其他模型为 0，所以排名指的是”模型–端点配置”；wall-clock 含端点延迟和 harness 开销，可能略超 60 分钟预算线。

10. 局限与批判

  • 无公开 artifact：代码、评测 harness、验证过的 range、攻击链、Exploit Guides、PoCs、轨迹全部走”受控 research-only + 安全审查”发布，没有 GitHub / Hugging Face / Zenodo 镜像。当前能复现的只有数据来源（Vulhub、CVE-Factory）和论文里的 schema/协议。
  • 拓扑受限：只有三层线性链（DMZ → 内网应用 → 数据网）；Windows 域、云 IAM、分支攻击图明确 out of scope。287 条链都是真实 CVE，但自动组合的 95% 环境有效 / 60% 端到端有效差距说明 CVE 组合覆盖并不穷尽。
  • 模型覆盖窄：四个模型里三个是中国前沿（Kimi-K3、GLM-5.2、DeepSeek-V4-Pro）加 GPT-5.6-Luna；Claude、Gemini、GPT-5.6 Sol/Terra 都没测，跨实验室比较无从谈起。
  • 验证器依赖：构造与验证全部用 DeepSeek-V4-Pro + 其执行产物；8% 误拒率意味着 62.4% 的验证通过率是”该协议下”的数字，被拒候选不等于无效。论文用 Kimi-K3 复检做敏感性审计，但没有把误拒校准进任何报告指标。
  • witness 语义：验证通过 = 存在一条成功路径，不排除更短或不同的替代路径；审计也明确不做 recall 估计。
  • 轨迹标注 schema 未公开：”outcome-annotated”的中间步骤、决策理由、完整工具序列如何标注，论文正文没有文档。
  • 防御侧不测：检测、响应、修补性能不在 RangeBench 里（它只定位攻击能力评测）。
  • 不可横向对比：和 CyberChainBench（智能合约 detect/exploit/patch）、PACEbench（A/B/C/D 任务集）任务分布完全不同，成功率数字不能直接比较；和 AgentCyberRange 一样，都是”自己定义的协议下的 pass@1”。

11. 值得借鉴 / 后续

  • 把 Atom 抽象搬进内部红队：RangeFactory 最大的工程价值是”每个漏洞环境只打一次，产物复用”，用真实攻击而不是元数据来决定链能不能接。内部渗透环境搭建可以完全复用这套能力依赖本体 + 闭包规则。
  • sustained-compromise gap 是训练信号：49.9% 的端到端 vs 明显更高的入口成功率，差的就是”拿下立足点之后”的长程能力；轨迹语料的 milestone turns 正好能给 outcome-aware 训练做对比锚点。
  • 标准化立足点解耦：论文自己指出，要分开”后续利用难度”和”长程状态维护”需要 standardized-foothold runs，这可以做成下一版 benchmark 的设计项。
  • 双验证器是底线：单验证器 8% 误拒提示所有自动构造 benchmark 都要做验证器敏感性审计；更理想的是构造/评测用不同模型（论文只对评测做了模型分离，构造侧没有）。
  • 等公开镜像：关注论文是否放出带 license 的永久镜像，在此之前无法复现、无法做二次实验。
